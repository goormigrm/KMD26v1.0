# KMD26 · 개리그 매니저 듀얼

사용자끼리 **전술로 대전**하는 축구 감독 게임입니다.
서버가 없습니다. 라인업을 코드로 만들어 링크로 주고받으면, 양쪽 브라우저에서 **완전히 동일한 경기**가 재생됩니다.

```
[A] 라인업 작성 → 초대 링크 게시판에 올림
[B] 링크 클릭 → 자기 라인업 작성 → 경기 관람 → 결과 링크를 A에게
[A] 결과 링크 열기 → 토씨 하나 안 틀리고 같은 경기
```

> 🚧 **개발 중입니다.** 현재 **단계 3(전술 반영 검증)** 진행 중입니다.

## 단계 3 — 전술 반영 검증

<https://goormigrm.github.io/KMD26v1.0/test/tactics.html>

전술 슬라이더를 극단으로 옮겼을 때 경기가 실제로 달라지는지, 기대한 방향으로 달라지는지 봅니다.

| 버튼 | 확인하는 것 | 통과 조건 | 경기 수 |
|---|---|---|---|
| **① 반영 여부만 즉시 확인** | 엔진이 그 값을 읽기는 하는가 | 9종 모두 **지문이 달라짐** | 18판 |
| **② 전체 항목 측정** | 기대한 방향으로 움직이는가 | 항목별 **75% 이상**의 쌍이 같은 방향 | 16쌍 × 9항목 = 288판 |
| **③ 한 항목만** | 위와 같음 | 위와 같음 | 32판 |

같은 시드로 짝을 지어 낮은 값·높은 값을 나란히 돌리기 때문에, 적은 표본으로도 차이가 드러납니다.

> ⏱ **경기 한 판이 약 8초입니다.** 13,500틱 동안 22명이 각자 판단하니 원래 무거운 일이고,
> 줄일 수 있는 종류의 비용이 아닙니다. 대신 판이 서로 독립이라 **Web Worker 로 코어를 나눠 씁니다**
> (설계서 §1-2). 화면에 남은 시간이 실시간으로 표시됩니다.
> 코어를 8개 쓰면 ①은 30초 안쪽, ②는 5~8분 정도입니다.

> 📌 **승률로 판정하지 않습니다.** 설계서의 "승률 3%p" 기준을 채우려면 항목당 수천 경기가 필요한데
> 브라우저가 감당할 양이 아닙니다. 승률 기준 판정은 **단계 9의 개발 전용 밸런스 도구**로 넘겼습니다.
> 대신 슬라이더가 직접 건드리는 지표(압박 → 태클 수 등)를 봅니다.

| 템포 | ✅ | 패스 수 |

| 수비 라인 | ✅ | 상대 오프사이드 |
| 폭 | ✅ | 크로스 |

| 역습 | ✅ | 패스 수 |

> ⚠️ **짧은 경기로는 놓칠 수 있습니다.** 15분 표본에서는 중거리 슛의 기본(2)과 적극(4)이

### ⭐ 측정으로 찾은 것 — "패스 길이"가 미반영이었습니다

같은 시드로 `pass=0`(짧게)과 `pass=4`(길게)를 돌렸더니 결과 지문이 **한 글자도 같았습니다.**
경기가 완전히 동일하다는 뜻입니다.

커널에서 `T.pass` 를 참조하는 곳은 `tacticSig()` — 전술이 바뀌었는지 감지하는 서명 문자열 하나뿐이고,
경기 계산에는 한 번도 쓰이지 않았습니다. `longGate`("몇 m부터 길게 차는가")도 선수 특성만 읽고
팀 지시는 안 봤습니다. **화면에 슬라이더를 띄워 놓고 아무 일도 안 일어나면 그건 거짓말입니다.**

| id | 어디에 | 무엇을 |
|---|---|---|
| `PASS-01` | `evaluatePassOptions` | 짧게면 거리 부담↑·전진 이득↓, 길게면 반대 — **목표 선택**이 달라진다 |
| `PASS-02` | 위 함수의 점수식 | 위 계수를 실제로 곱한다 |
| `PASS-03` | `longGate` | 길게 차는 문턱을 팀 지시로도 움직인다 — **차는 모양**이 따라온다 |

난수를 더 쓰지 않으므로 결정론에는 영향이 없습니다.

> 📌 v1 설계서의 "역습·템포가 2D 엔진에 미반영"은 사실이 아니었지만
> (`tempoK()`·`counterOn()` 둘 다 살아 있습니다), **같은 종류의 문제가 다른 슬라이더에 있었습니다.**
> "있다"를 확인하는 것과 "전부 있다"를 확인하는 것은 다릅니다.

### 측정 뒤 고친 것 (16쌍 · 2026-08-13)

| 항목 | 수정 전 | 조치 | 수정 후 |
|---|---|---|---|
| 압박 | 태클 시도 17.4 → 17.4 | `PRESS-01` `PRESS-02` | **15.7 → 20.0** |
| 멘탈리티 | 슈팅 14.3 → **12.3** (거꾸로) | `MENT-01` | **15.3 → 18.3** |

`tryTackle` 은 `T.press` 를 아예 안 읽었습니다. 압박을 올려도 더 달려들지 않았던 것입니다.

### ⛔ 남은 과제

**폭(width)** — 넓게 서면 오히려 크로스가 줍니다. 문턱에 팀 폭을 넣어 봤더니
(`WIDTH-01`) 10쌍에서 11.6 → 8.5 로 **더 나빠져서 꺼 두었습니다.**
넓게 서면 올릴 기회는 늘지만 **박스 안에 댈 사람이 줄어**(`inBoxMates` 가 비면 크로스 취소)
두 힘이 맞섭니다. 손볼 곳은 문턱이 아니라 "박스에 누가 들어가는가"입니다.

**템포** — 계수 이월 버그는 고쳤지만 여전히 약합니다. 볼 보유 시간만 건드려서는 한계가 있고,
패스 선택 자체에 연결해야 할 것으로 봅니다.

수정안은 지우지 않고 `tools/patch_kernel.py` 에 `off=True` 로 남겨 두었습니다 —
측정 근거와 다음에 볼 곳까지 주석에 있습니다. 자세한 내용은 설계서 "남은 과제" 참고.

### 브라우저 없이 확인하는 도구

이 저장소에는 Node 같은 로컬 JS 런타임이 없습니다. 그래서 Go 안에서 JS 를 돌립니다(goja).
데이터 파이프라인에서 쓴 방법을 그대로 씁니다 — ESM 모듈을 의존 순서대로 이어 붙이고
`import`/`export` 줄만 걷어내면 됩니다.

```bash
cd tools/jscheck && go run . ../../src ../../test      # 문법 검사 (.js + <script>)
cd tools/simcheck && go run . -root ../.. -key press   # 전술 슬라이더가 연결됐는지
```

`simcheck` 은 같은 시드로 슬라이더만 바꿔 두 판을 돌리고 결과 지문을 비교합니다.
지문이 같으면 엔진이 그 값을 안 읽는 것입니다 — **패스 길이 미반영을 이걸로 잡았습니다.**

> ⏱ goja 는 V8 보다 6배쯤 느립니다(정규 90분 ≈ 48초). 대량 측정에는 안 맞고,
> "연결됐는가"를 보는 용도입니다. 통계 측정은 브라우저의 `test/tactics.html` 로 합니다.
> 짧게 보려면 `-secs 900` 처럼 경기 길이를 줄이세요.

### 커널을 다시 뽑으려면

원본 KM26이 업데이트되면 두 줄만 돌리면 됩니다. 손으로 고칠 곳은 없습니다.

```bash
python tools/extract_engine.py <KM26 index.html 경로> src/engine/kernel.raw.js
python tools/patch_kernel.py src/engine/kernel.raw.js src/engine/kernel.js
```

추출기는 `MatchSim`에서 시작하는 **의존성 폐포**를 계산해 필요한 선언만 원본 순서대로 뽑습니다.
전역 상태·UI는 경계에서 끊고 `stubs.js`가 대신합니다.

### 두 단계로 나눈 이유

커널은 손으로 고치지 않는 게 원칙입니다. 그런데 KM26 원본 버그 중에는 함수 한복판에 있어서
바깥에서 감쌀 수 없는 것이 있습니다. 그것만 패치기가 처리하고, 나머지는 전부 래퍼로 갑니다.

| 어디에 | 무엇을 | 예 |
|---|---|---|
| `tools/patch_kernel.py` | 함수 한복판이라 감쌀 수 없는 **원본 버그 수정** | PK 3건 (아래) |
| `src/engine/rules.js` | 메서드 경계에서 표현되는 **듀얼 고유 규칙** | 누적 파울 · 퇴장 체력 |
| `src/engine/stubs.js` | 엔진이 참조하는 **전역 문맥** | `G` · `famK` · `refBias` |

패치는 "몇 군데에 걸려야 하는지"를 못박아 둡니다. 원본이 갱신돼 코드가 달라지면
조용히 건너뛰지 않고 **즉시 중단**됩니다.

셋 다 페널티킥 관련이고, 듀얼에 그대로 상속되던 것입니다.

| id | 증상 | 원인 |
|---|---|---|
| `PK-01` | PK 다음 킥오프에서 센터서클 한복판에 "페널티킥"이 선언됨 | `kickoff()` 이 `b.isPenalty` 를 초기화하지 않음 |
| `PK-02` | PK 득점이 VAR 로 취소됨 | 2D 엔진에 `isPen` 가드가 없음 (분 단위 엔진에는 있음) |
| `PK-03` | 90분 종료 직전에 선언된 PK 가 실행되지 않음 | 시뮬 루프가 시계만 보고 끝냄 |

| 원칙 | 이유 |
|---|---|
| **커널은 절대 손대지 않는다** | 원본이 갱신되면 다시 뽑아야 하므로. 고칠 게 있으면 래퍼(`rules.js`)에서, 그래도 안 되면 패치기에서 |
| **패치는 걸린 횟수를 못박는다** | 원본이 바뀌어 패치가 빗나가면 조용히 넘어가는 대신 즉시 멈추도록 |
| **시즌 누적값은 전부 고정** | 조직력 100 · 사기 75 · 컨디션 100. "누가 시즌을 오래 굴렸는가"가 승부에 끼어들면 안 됨 |
| **포지션 능숙도는 유지** | 이게 없으면 라인업을 짤 이유가 사라짐 |
| **시드는 양쪽 코드에서 유도** | 어느 쪽도 유리한 결과를 골라 공유할 수 없게 |

전체 설계는 `개리그매니저듀얼_설계서_v2.md` 를 보세요.

## 단계 4 — 데이터 파이프라인

29개 구단 **1,024명**의 실제 선수를 `data/*.json` 으로 뽑아 둡니다.

```bash
python tools/extract_data.py <KM26 index.html 경로> src/data/gen.js
cd tools/gendata
go run . -root ../..
```

### 능력치를 옮겨 적지 않고 원본 함수를 그대로 돌립니다

원본 안에 선수 능력치가 통째로 들어 있지는 않습니다. 들어 있는 건 표 세 개뿐입니다.

| 표 | 내용 |
|---|---|
| `D1` | K리그1 12개 구단 — 손으로 매긴 `ovr` 이 있는 명단 |
| `D2` | K리그2 17개 구단 — 팀 수준(`base`)과 간판 선수 몇 명 |
| `ROSTER26` | 29개 구단 실제 등록 명단 1,024명 (이름·포지션·생년월일·등번호·키·몸무게, **능력치 없음**) |

세부 능력치 40여 종은 `mkPlayer()` 가 만들어 냅니다. 그 안에 포지션 특화 · 나이 감쇠 ·
신장 보정 · 특성 추첨이 겹겹이 들어 있어서, **다른 언어로 옮겨 적으면 반드시 어긋납니다.**
값이 달라지면 "같은 선수"가 아니게 되고 검토 기준 자체가 무너집니다.

그래서 옮겨 적지 않고 **원본 함수를 그대로 뽑아 한 번 돌립니다.** 엔진 커널과 같은 방법입니다.
Go 도구가 그 JS 를 실행(goja)하고, 고르고, 검증하고, 저장합니다.

```
index.html ──extract_data.py──> src/data/gen.js ──go run ./tools/gendata──> data/*.json
             (의존성 폐포 + 시드화)              (실행 · 정리 · 검증 · 해시)
```

### 확인한 것

| 검증 | 결과 |
|---|---|
| 선수 수 | 1,024명 — 원본 명단과 일치 |
| 재현성 | 같은 시드 → 바이트 단위로 같은 파일 |
| 선호 포지션 우선순위 | 안양 마테우스 = **CAM** (`PLAYER_TWEAK` 이 최종 승자) |
| 구단별 정합 | 29개 구단 전부 골키퍼 보유 · 12명 이상 · `attr`/`posFam` 누락 0 |

> 📌 **`ovr` 은 표 값 그대로가 아닙니다.** `applyAgeDecline` 이 나이 감쇠만큼 같이 내립니다.
> (조현우 80 → 78, 35세) 원본 설계가 그렇습니다.

### ⚠ 발견한 원본 버그 — K리그2 간판 선수의 능력치가 무시됩니다

`mkTeam` 이 수기 능력치를 찾을 때 `d.players` 만 봅니다. 그런데 **K리그2 항목은 그 값을 `stars` 에 담고 있어서**,
K2 선수는 전원 추정값(`estimateOvr`)으로 덮입니다.

| 선수 | 표 | 실제 생성 |
|---|---|---|
| 세징야 (대구) | 74 | **63** |
| 양형모 (수원) | 74 | **64** |
| 발디비아 (전남) | 75 | **68** |

밸런스에 직결되므로 **아직 고치지 않았습니다.** 원본에도 이슈로 올릴 값어치가 있습니다.

## 단계 6 — 라인업 편집 화면

<https://goormigrm.github.io/KMD26v1.0/lineup.html>

KM26 과 같은 **한 줄 5칸 격자** 전술판입니다. 이 게임을 할 사람들은 이미 개리그 매니저에
익숙하므로 형태를 그대로 씁니다.

| | 방법 |
|---|---|
| 마우스 | 끌어서 놓기. 전술판 안에서 끌면 두 선수가 맞바뀝니다 |
| 손가락 | 자리와 선수를 차례로 누르기 — 순서는 아무래도 좋습니다 |

명단은 KM26 처럼 **선발 / 교체 명단(S1~S9) / 그 외 명단** 셋으로 나뉩니다.
교체 명단은 목록이 아니라 **자리가 아홉 개**라 순서가 눈에 보입니다.

**자리에 안 맞는 선수도 세울 수 있습니다.** 걸러내지 않고 능숙도 색으로만 알립니다 —
지고 있을 때 센터백을 최전방에 올리는 건 실제로 하는 일이니까요.

역할·임무도 고를 수 있습니다. 엔진이 `tactic.role[선수id]` 를 읽으므로 경기에 그대로 반영됩니다.
그 자리에서 맡을 수 없는 역할이면 자리 기본값으로 되돌아갑니다 — 커널 `getRole` 과 같은 판정입니다.

### 별점은 눈금이 하나입니다

KM26 은 1군 수준에 못 미치는 선수를 **은색 눈금**으로 갈아태웁니다. 시즌 게임에서는
유스와 1군을 갈라 보여 주는 장치라 뜻이 있지만, 듀얼에서는 해롭습니다 —
금색 2.5개짜리 주전보다 은색 3.5개짜리 후보가 **별이 많아 보입니다.** 실제로는 한참 아래인데도요.

듀얼은 육성도 잠재력도 없고 오로지 지금 실력으로 겨루므로 눈금을 하나로 합쳤습니다.
K리그1·2 전체 선수의 실력 분포에서 **하위 2%가 0.5★, 상위 2%가 5★** 입니다.
별이 많을수록 언제나 더 나은 선수입니다.

### 연습 모드 (단계 A)

상대가 없어도 혼자 전술을 시험해 볼 수 있어야 한다는 의견을 받아 넣기로 했습니다.
팀마다 **3난이도 × 상대 전술 3종 = 아홉 가지** 연습 상대가 생깁니다.

난이도는 **능력치를 올려서 만들지 않습니다.** 그러면 "전력이 떨어져도 전술로 이기는 재미"가 무너집니다.
대신 상대 감독이 얼마나 유능한지를 바꿉니다 — 라인업을 잘 짜는가, 경기 중에 대응하는가,
내 전술을 보고 상성으로 골라 오는가.

연습 모드는 코드·링크 규격이 필요 없어서 **대전보다 먼저 나옵니다.** 자세한 설계는 설계서 단계 A.
