# KMD26 · 개리그 매니저 듀얼

사용자끼리 **전술로 대전**하는 축구 감독 게임입니다.
서버가 없습니다. 라인업을 코드로 만들어 링크로 주고받으면, 양쪽 브라우저에서 **완전히 동일한 경기**가 재생됩니다.

```
[A] 라인업 작성 → 초대 링크 게시판에 올림
[B] 링크 클릭 → 자기 라인업 작성 → 경기 관람 → 결과 링크를 A에게
[A] 결과 링크 열기 → 토씨 하나 안 틀리고 같은 경기
```

> 🚧 **개발 중입니다.** 현재 **단계 3(전술 반영 검증)** 진행 중입니다.

## 단계 3 — 전술 반영 검증

<https://goormigrm.github.io/KMD26v1.0/test/tactics.html>

전술 슬라이더를 극단으로 옮겼을 때 경기가 실제로 달라지는지, 기대한 방향으로 달라지는지 봅니다.

| 버튼 | 확인하는 것 | 통과 조건 | 경기 수 |
|---|---|---|---|
| **① 반영 여부만 즉시 확인** | 엔진이 그 값을 읽기는 하는가 | 9종 모두 **지문이 달라짐** | 18판 |
| **② 전체 항목 측정** | 기대한 방향으로 움직이는가 | 항목별 **75% 이상**의 쌍이 같은 방향 | 16쌍 × 9항목 = 288판 |
| **③ 한 항목만** | 위와 같음 | 위와 같음 | 32판 |

같은 시드로 짝을 지어 낮은 값·높은 값을 나란히 돌리기 때문에, 적은 표본으로도 차이가 드러납니다.

> ⏱ **경기 한 판이 약 8초입니다.** 13,500틱 동안 22명이 각자 판단하니 원래 무거운 일이고,
> 줄일 수 있는 종류의 비용이 아닙니다. 대신 판이 서로 독립이라 **Web Worker 로 코어를 나눠 씁니다**
> (설계서 §1-2). 화면에 남은 시간이 실시간으로 표시됩니다.
> 코어를 8개 쓰면 ①은 30초 안쪽, ②는 5~8분 정도입니다.

> 📌 **승률로 판정하지 않습니다.** 설계서의 "승률 3%p" 기준을 채우려면 항목당 수천 경기가 필요한데
> 브라우저가 감당할 양이 아닙니다. 승률 기준 판정은 **단계 9의 개발 전용 밸런스 도구**로 넘겼습니다.
> 대신 슬라이더가 직접 건드리는 지표(압박 → 태클 수 등)를 봅니다.

### ⭐ 측정으로 찾은 것 — "패스 길이"가 미반영이었습니다

같은 시드로 `pass=0`(짧게)과 `pass=4`(길게)를 돌렸더니 결과 지문이 **한 글자도 같았습니다.**
경기가 완전히 동일하다는 뜻입니다.

커널에서 `T.pass` 를 참조하는 곳은 `tacticSig()` — 전술이 바뀌었는지 감지하는 서명 문자열 하나뿐이고,
경기 계산에는 한 번도 쓰이지 않았습니다. `longGate`("몇 m부터 길게 차는가")도 선수 특성만 읽고
팀 지시는 안 봤습니다. **화면에 슬라이더를 띄워 놓고 아무 일도 안 일어나면 그건 거짓말입니다.**

| id | 어디에 | 무엇을 |
|---|---|---|
| `PASS-01` | `evaluatePassOptions` | 짧게면 거리 부담↑·전진 이득↓, 길게면 반대 — **목표 선택**이 달라진다 |
| `PASS-02` | 위 함수의 점수식 | 위 계수를 실제로 곱한다 |
| `PASS-03` | `longGate` | 길게 차는 문턱을 팀 지시로도 움직인다 — **차는 모양**이 따라온다 |

난수를 더 쓰지 않으므로 결정론에는 영향이 없습니다.

> 📌 v1 설계서의 "역습·템포가 2D 엔진에 미반영"은 사실이 아니었지만
> (`tempoK()`·`counterOn()` 둘 다 살아 있습니다), **같은 종류의 문제가 다른 슬라이더에 있었습니다.**
> "있다"를 확인하는 것과 "전부 있다"를 확인하는 것은 다릅니다.

### 측정 뒤 고친 것 (16쌍 · 2026-08-13)

| 항목 | 수정 전 | 조치 | 16쌍 재측정 |
|---|---|---|---|
| 압박 | 태클 시도 17.4 → 17.4 (5/16) | `PRESS-01` `PRESS-02` | ✅ **+44% · 13/16 뚜렷** |
| 템포 | 패스 수 +5.4% (11/16 약함) | `TEMPO-01` | ✅ **+13% · 14/16 뚜렷** |
| 멘탈리티 | 슈팅 14.3 → **12.3** (거꾸로) | `MENT-01` | ❌ **여전히 거꾸로** (-10%, 6/16) |
| 폭 | 크로스 +16% (9/16 잡음) | ⛔ **보류** | ❌ 그대로 (9/16) |

> ⚠️ **멘탈리티는 못 고쳤습니다.** 3쌍 표본에서 좋아진 것처럼 보였으나(15.3→18.3)
> 16쌍에서는 여전히 뒤집혀 있습니다. **적은 표본으로 "고쳤다"고 판단하면 안 됩니다.**
> `MENT-01` 은 방향이 맞으므로 켜 둔 채로 두었습니다 — 끄면 더 나빠집니다.

압박은 진짜 배선 오류였습니다. `pressureOn` 이 **압박당하는 쪽**의 지시로 계수를 계산했고,
`tryTackle` 은 `T.press` 를 아예 안 읽었습니다. 압박을 올려도 더 달려들지 않았던 것입니다.

### ⛔ 남은 과제

**폭(width)** — 넓게 서면 오히려 크로스가 줍니다. 문턱에 팀 폭을 넣어 봤더니
(`WIDTH-01`) 10쌍에서 11.6 → 8.5 로 **더 나빠져서 꺼 두었습니다.**
넓게 서면 올릴 기회는 늘지만 **박스 안에 댈 사람이 줄어**(`inBoxMates` 가 비면 크로스 취소)
두 힘이 맞섭니다. 손볼 곳은 문턱이 아니라 "박스에 누가 들어가는가"입니다.

**템포** — 계수 이월 버그는 고쳤지만 여전히 약합니다. 볼 보유 시간만 건드려서는 한계가 있고,
패스 선택 자체에 연결해야 할 것으로 봅니다.

수정안은 지우지 않고 `tools/patch_kernel.py` 에 `off=True` 로 남겨 두었습니다 —
측정 근거와 다음에 볼 곳까지 주석에 있습니다. 자세한 내용은 설계서 "남은 과제" 참고.

### 브라우저 없이 확인하는 도구

이 저장소에는 Node 같은 로컬 JS 런타임이 없습니다. 그래서 Go 안에서 JS 를 돌립니다(goja).
데이터 파이프라인에서 쓴 방법을 그대로 씁니다 — ESM 모듈을 의존 순서대로 이어 붙이고
`import`/`export` 줄만 걷어내면 됩니다.

```bash
cd tools/jscheck && go run . ../../src ../../test      # 문법 검사 (.js + <script>)
cd tools/simcheck && go run . -root ../.. -key press   # 전술 슬라이더가 연결됐는지
```

`simcheck` 은 같은 시드로 슬라이더만 바꿔 두 판을 돌리고 결과 지문을 비교합니다.
지문이 같으면 엔진이 그 값을 안 읽는 것입니다 — **패스 길이 미반영을 이걸로 잡았습니다.**

> ⏱ goja 는 V8 보다 6배쯤 느립니다(정규 90분 ≈ 48초). 대량 측정에는 안 맞고,
> "연결됐는가"를 보는 용도입니다. 통계 측정은 브라우저의 `test/tactics.html` 로 합니다.
> 짧게 보려면 `-secs 900` 처럼 경기 길이를 줄이세요.

### 커널을 다시 뽑으려면

원본 KM26이 업데이트되면 두 줄만 돌리면 됩니다. 손으로 고칠 곳은 없습니다.

```bash
python tools/extract_engine.py <KM26 index.html 경로> src/engine/kernel.raw.js
python tools/patch_kernel.py src/engine/kernel.raw.js src/engine/kernel.js
```

추출기는 `MatchSim`에서 시작하는 **의존성 폐포**를 계산해 필요한 선언만 원본 순서대로 뽑습니다.
전역 상태·UI는 경계에서 끊고 `stubs.js`가 대신합니다.

### 두 단계로 나눈 이유

커널은 손으로 고치지 않는 게 원칙입니다. 그런데 KM26 원본 버그 중에는 함수 한복판에 있어서
바깥에서 감쌀 수 없는 것이 있습니다. 그것만 패치기가 처리하고, 나머지는 전부 래퍼로 갑니다.

| 어디에 | 무엇을 | 예 |
|---|---|---|
| `tools/patch_kernel.py` | 함수 한복판이라 감쌀 수 없는 **원본 버그 수정** | PK 3건 (아래) |
| `src/engine/rules.js` | 메서드 경계에서 표현되는 **듀얼 고유 규칙** | 누적 파울 · 퇴장 체력 |
| `src/engine/stubs.js` | 엔진이 참조하는 **전역 문맥** | `G` · `famK` · `refBias` |

패치는 "몇 군데에 걸려야 하는지"를 못박아 둡니다. 원본이 갱신돼 코드가 달라지면
조용히 건너뛰지 않고 **즉시 중단**됩니다.

### 고친 KM26 원본 버그

셋 다 페널티킥 관련이고, 듀얼에 그대로 상속되던 것입니다.

| id | 증상 | 원인 |
|---|---|---|
| `PK-01` | PK 다음 킥오프에서 센터서클 한복판에 "페널티킥"이 선언됨 | `kickoff()` 이 `b.isPenalty` 를 초기화하지 않음 |
| `PK-02` | PK 득점이 VAR 로 취소됨 | 2D 엔진에 `isPen` 가드가 없음 (분 단위 엔진에는 있음) |
| `PK-03` | 90분 종료 직전에 선언된 PK 가 실행되지 않음 | 시뮬 루프가 시계만 보고 끝냄 |

> 📮 원본에도 이슈로 올릴 값어치가 있습니다 — 백로그에 있습니다.

## 단계 4 — 데이터 파이프라인

29개 구단 **1,024명**의 실제 선수를 `data/*.json` 으로 뽑아 둡니다.

```bash
python tools/extract_data.py <KM26 index.html 경로> src/data/gen.js
cd tools/gendata
go run . -root ../..
```

### 능력치를 옮겨 적지 않고 원본 함수를 그대로 돌립니다

원본 안에 선수 능력치가 통째로 들어 있지는 않습니다. 들어 있는 건 표 세 개뿐입니다.

| 표 | 내용 |
|---|---|
| `D1` | K리그1 12개 구단 — 손으로 매긴 `ovr` 이 있는 명단 |
| `D2` | K리그2 17개 구단 — 팀 수준(`base`)과 간판 선수 몇 명 |
| `ROSTER26` | 29개 구단 실제 등록 명단 1,024명 (이름·포지션·생년월일·등번호·키·몸무게, **능력치 없음**) |

세부 능력치 40여 종은 `mkPlayer()` 가 만들어 냅니다. 그 안에 포지션 특화 · 나이 감쇠 ·
신장 보정 · 특성 추첨이 겹겹이 들어 있어서, **다른 언어로 옮겨 적으면 반드시 어긋납니다.**
값이 달라지면 "같은 선수"가 아니게 되고 검토 기준 자체가 무너집니다.

그래서 옮겨 적지 않고 **원본 함수를 그대로 뽑아 한 번 돌립니다.** 엔진 커널과 같은 방법입니다.
Go 도구가 그 JS 를 실행(goja)하고, 고르고, 검증하고, 저장합니다.

```
index.html ──extract_data.py──> src/data/gen.js ──go run ./tools/gendata──> data/*.json
             (의존성 폐포 + 시드화)              (실행 · 정리 · 검증 · 해시)
```

### 확인한 것

| 검증 | 결과 |
|---|---|
| 선수 수 | 1,024명 — 원본 명단과 일치 |
| 재현성 | 같은 시드 → 바이트 단위로 같은 파일 |
| 선호 포지션 우선순위 | 안양 마테우스 = **CAM** (`PLAYER_TWEAK` 이 최종 승자) |
| 구단별 정합 | 29개 구단 전부 골키퍼 보유 · 12명 이상 · `attr`/`posFam` 누락 0 |

> 📌 **`ovr` 은 표 값 그대로가 아닙니다.** `applyAgeDecline` 이 나이 감쇠만큼 같이 내립니다.
> (조현우 80 → 78, 35세) 원본 설계가 그렇습니다.

|---|---|---|
| 세징야 (대구) | 74 | **63** |

밸런스에 직결되므로 **아직 고치지 않았습니다.** 원본에도 이슈로 올릴 값어치가 있습니다.

## 단계 6 — 라인업 편집 화면

<https://goormigrm.github.io/KMD26v1.0/lineup.html>

KM26 과 같은 **한 줄 5칸 격자** 전술판입니다. 이 게임을 할 사람들은 이미 개리그 매니저에
익숙하므로 형태를 그대로 씁니다. 격자 뒤에는 **코트를 깔았습니다** — 중앙선·센터서클·
페널티박스·골에어리어. 격자만 있으면 그 자리가 경기장 어디쯤인지 감이 안 옵니다.
칸 크기는 오른쪽 선발 명단 한 줄과 맞췄습니다(이름이 잘리지 않는 크기).

| | 방법 |
|---|---|
| 마우스 | 끌어서 놓기. 전술판 안에서 끌면 두 선수가 맞바뀝니다 |
| 손가락 | 자리와 선수를 차례로 누르기 — 순서는 아무래도 좋습니다 |

### 저장 슬롯이 맨 위입니다

짜 둔 라인업이 있으면 **구단을 고르기 전에 그것부터 불러오는 게 순서**입니다. 불러오면
구단·포메이션·전술·배치가 한꺼번에 올라옵니다. 그래서 슬롯 카드를 구단 선택보다 위에 둡니다.

슬롯은 **누르면 바로 적용하지 않고 한 번 묻습니다.** 한 칸에 열한 명과 전술이 다 들어 있어서
잘못 누르면 짜 둔 것이 한 번에 사라집니다. 불러오기·덮어쓰기·지우기 셋 다 묻고,
빈 칸에 저장하는 것만 바로 합니다(잃을 것이 없으므로).

### 선수 프로필 — 페이지를 옮기지 않습니다

선수 옆 **프로필** 버튼을 누르면 그 자리에서 세부 능력치가 열립니다 —
기술·정신·신체·골키퍼 능력치, 포지션 능숙도 17칸, 특성, 그리고 **지금 서 있는 자리의 능숙도**.
선수단 화면으로 넘어가면 짜던 라인업이 날아가기 때문입니다. 이름표는 `data/teams.json` 의
`labels` 를 씁니다 — 화면에 베껴 두면 원본이 바뀔 때 어긋납니다.

명단은 KM26 처럼 **선발 / 교체 명단(S1~S9) / 그 외 명단** 셋으로 나뉩니다.
교체 명단은 목록이 아니라 **자리가 아홉 개**라 순서가 눈에 보입니다.

**자리에 안 맞는 선수도 세울 수 있습니다.** 걸러내지 않고 능숙도 색으로만 알립니다 —
지고 있을 때 센터백을 최전방에 올리는 건 실제로 하는 일이니까요.

역할·임무도 고를 수 있습니다. 엔진이 `tactic.role[선수id]` 를 읽으므로 경기에 그대로 반영됩니다.
그 자리에서 맡을 수 없는 역할이면 자리 기본값으로 되돌아갑니다 — 커널 `getRole` 과 같은 판정입니다.

### 별점은 눈금이 하나입니다

KM26 은 1군 수준에 못 미치는 선수를 **은색 눈금**으로 갈아태웁니다. 시즌 게임에서는
유스와 1군을 갈라 보여 주는 장치라 뜻이 있지만, 듀얼에서는 해롭습니다 —
금색 2.5개짜리 주전보다 은색 3.5개짜리 후보가 **별이 많아 보입니다.** 실제로는 한참 아래인데도요.

듀얼은 육성도 잠재력도 없고 오로지 지금 실력으로 겨루므로 눈금을 하나로 합쳤습니다.
K리그1·2 전체 선수의 실력 분포에서 **하위 2%가 0.5★, 상위 2%가 5★** 입니다.
별이 많을수록 언제나 더 나은 선수입니다.

## 단계 7 — 경기 재생 화면

<https://goormigrm.github.io/KMD26v1.0/match.html>

라인업 화면의 **▶ 이 라인업으로 경기** 를 누르면 선발·교체·전술·역할이 그대로 엔진에 들어갑니다.
대진 칸에서는 **양쪽 모두** 라인업을 고를 수 있습니다 — 자동 · 라인업 화면에서 짠 것 ·
저장 슬롯 열 벌. 그 구단으로 저장한 것만 목록에 나옵니다.

### 같은 구단끼리도 붙습니다

**울산 vs 울산** 이 됩니다. 선수와 전술이 다르면 다른 팀이니까요.
막는 것은 단 하나 — **라인업 지문이 완전히 같을 때**입니다(선발·교체·전술·역할이 한 글자도
다르지 않은 경우). 그때는 두 팀을 가릴 것이 없습니다.

같은 구단이면 두 가지를 갈라 놓습니다.

| 무엇 | 어떻게 | 왜 |
|---|---|---|
| 선수 id | 원정 쪽에 **+100000** | 커널은 22명을 한 배열에 담고 id 로 찾습니다(`byId`). 겹치면 원정 슈터를 찾을 때 홈 선수가 잡힙니다 |
| 이름·색 | `(홈)` · `(어웨이)` · 원정은 `col2` | 해설·팬 반응·2D 에서 어느 쪽인지 알아야 합니다. 게다가 커널 `ev()` 는 "직전 줄과 같은 팀인가"를 **이름표로** 판단해 시간 배지를 생략합니다 |

> ⚠️ 옮긴 id 는 **엔진 안에서만** 삽니다. 시드(= 단계 5 의 대전 코드)는 반드시 옮기기 **전**
> 라인업으로 뽑아야 두 사람의 코드가 같은 값을 냅니다.

### 전술판의 모양과 자리가 엔진까지 갑니다

라인업 화면이 넘기던 값에 **포메이션이 빠져 있었고**(경기는 늘 4-3-3 으로 섰습니다),
전술판에서 끌어다 놓은 **자리 표도 비워서 넘겼습니다**(커널이 전부 자동 재배치했습니다).
둘 다 이제 그대로 갑니다 — `tactic.formation` 과 `tactic.slot` 입니다.
커널 `computeRenderSlots()` 는 감독이 지정한 자리를 최우선으로 지키고, 남은 선수만
그 포메이션의 빈 자리에 앉힙니다. 옛 저장본에 포메이션이 없으면 자리 이름 묶음으로 되찾습니다.

**실시간으로 한 틱씩 돌려 보여 주지 않습니다.** 먼저 끝까지 다 돌린 뒤 이벤트를 분 단위로
풀어놓는 **재생** 방식입니다. 실시간이면 엔진 속도가 곧 배속 상한이 되지만, 다 돌려 놓고 재생하면
1·2·4배속도 끝까지 건너뛰기도 공짜입니다.

전광판은 이벤트에 박혀 있는 **그 순간의 점수**를 따릅니다 — 원본이 그러라고 넣어 둔 값이고,
안 그러면 점수가 골 해설보다 먼저 올라갑니다.

```
src/engine/teams.js        data/*.json → 엔진 팀 객체 · 자동 라인업 · 라인업 검사
src/engine/matchworker.js  경기를 따로 떼어 돌린다 (한 판 8초라 화면이 멈친다)
match.html                 전광판 · 해설 재생 · 배속 · 경기 기록
```

### 2D 하이라이트

결정적 장면이 나오면 **시계를 멈추고 그 장면을 캔버스로 보여 준 뒤** 이어서 재생합니다.
경기가 끝나면 목록에서 다시 볼 수 있습니다.

**필드는 항상 서 있습니다.** 예전에는 골이 없으면 캔버스를 아예 띄우지 않아
0:0 경기에서는 필드가 한 번도 안 그려졌습니다. 이제 킥오프 포메이션을 세워 두고,
장면이 끝나면 그 **마지막 프레임에서 정지**한 채로 시간이 흘러갑니다
(KM26 의 `MATCH_MODE.TEXT` — "정지된 포메이션 위에 자막만" 과 같은 자리입니다).

| 무엇 | 어떻게 |
|---|---|
| 어디까지 볼까 | `결정적 장면 전부`(기본) · `골만` · `안 보기`. 엔진이 매긴 무게로 가릅니다 — 결정적 기회 1 · 선방 2 · 퇴장 3 · PK 4 · 골 5 (커널 `HL_W`) |
| 골 리플레이 | 골 장면이 끝나면 **골 순간 앞 6초·뒤 2.5초를 0.62배속으로 한 번 더**. KM26 의 `HL_REPLAY_PRE/POST/RATE` 를 그대로 옮겼습니다. 되풀이는 하지 않습니다 |
| ↺ 다시 보기 | 방금 본 장면을 손으로 다시. 정지 화면에서도 누를 수 있습니다 |
| 배속 | **장면 재생에도 걸립니다** (KM26 `HL_RATE × liveMul()`). 한 경기에 장면이 스무 개면 전체 시간이 장면에 지배되므로, 해설 간격만 바꾸면 1·2·4배속 차이가 느껴지지 않습니다. 보고 있던 장면도 그 자리에서 새 배속으로 이어집니다 (실측: 같은 장면 1배속 2,699ms → 4배속 855ms) |

### 득점자 패널

골이 들어가는 순간 화면 가운데에 **GOAL! · 득점자 · 도움**을 크게 띄웁니다(KM26 `goalPanel`).
빌드업이 재생되는 동안에는 띄우지 않습니다 — 결과를 미리 알려 주는 꼴이 되기 때문입니다.
클립에 담아 둔 `trig`(장면이 잡힌 지점)에 닿는 순간부터 뜨고, 리플레이 중에는 걷습니다.

> ⚠️ 커널은 **오프사이드·VAR 로 취소된 골에도** `markHighlight("goal")` 을 붙입니다.
> 득점 기록(`goalLine`)에 없으면 취소된 것으로 보고 **NO GOAL** 패널을 띄우고,
> 다시 보기 목록에도 `득점 취소` 로 적습니다. 예전에는 이것까지 "골"로 세어
> 한 골도 안 난 팀에게 골 장면이 두 개 있는 것처럼 보였습니다.

도움 이름은 커널이 `M.sc` 에 담지 않고 해설 문장 안에만 넣습니다. 문장을 되짚어 이름을
뽑아내는 건 깨지기 쉬우므로, `recordGoal` 을 감싸 `goalTag.aid` 에서 받아 적습니다
(`src/engine/replay.js`). 커널은 손대지 않습니다.

### 해설은 아래에서 위로 쌓입니다

가장 새 줄이 **맨 위**, 필드 화면 바로 아래에 옵니다. 짧을 때는 바닥에 붙어 있습니다.

한 경기에 장면이 19~24개 나옵니다. 골만 보던 것에 비하면 필드에서 벌어지는 일이
훨씬 많이 보입니다 — 선방·결정적 기회·퇴장도 경기의 일부입니다.

필드 그림과 바둑알 크기는 KM26 `drawPitchBase` 에 맞췄습니다 —
골 에어리어·골대·페널티 스폿까지 있어야 "골문 앞"이 어디인지 눈에 들어옵니다.

90분 전체를 그리지 않는 이유는 단순합니다 — 재생이 90분을 1분에 흘려보내므로
1분당 150장을 그려야 합니다. 사람이 볼 수 있는 속도가 아닙니다. 원본 엔진도 그래서
링버퍼(52초)에 최근 장면만 들고 다니며 `markHighlight()` 로 결정적 순간을 짚어 둡니다.
그 표시를 따라 **앞 8초·뒤 5초**를 잘라 모읍니다 (한 경기 약 20클립 · 490KB).

> ⚠️ **`sim.recording` 은 절대 끄면 안 됩니다.** 커널에 `if(this.recording && RNG()<…)` 가 있어
> 끄는 순간 난수 흐름이 달라져 **다른 경기**가 됩니다. 2D 를 보든 안 보든 같은 경기여야 하므로,
> 켜고 끄는 것은 클립 수집(`_wantClips`)뿐입니다.

### 경기 뒤 반응 — 소셜미디어 · FM코리아

경기가 끝나면 팬들이 떠듭니다. 문구·계정 이름·더비 표를 KM26 에서 그대로 가져왔습니다
(`data/reactions.json`). **양쪽 팬 시선을 바꿔** 볼 수 있고, 같은 경기면 반응도 같아야 하므로
경기가 끝난 뒤 시드를 다시 심고 뽑습니다.

원본을 그대로 따라간 것:

| 무엇 | 어떻게 |
|---|---|
| 우리 팬 · 남의 팬 | 표가 **아예 다릅니다**(`SOC/FMK` ↔ `RIV/FRIV`). 같은 경기를 남의 눈으로 본 글은 결이 다릅니다. 한 피드에 섞여 올라오고, 타팬 글에는 이름표가 붙습니다 |
| 계정 이름 | 이모지가 붙고 일부 풀은 뒤에 숫자가 붙습니다(`원정석구석4821 🧳`). 여섯 개 풀 131개 — 뽑는 확률까지 원본 `socHandle()`/`rivalHandle()` 그대로입니다 |
| 펨코 글 | 추천·비추·조회수가 붙습니다. 나쁜 소식에는 **상주 악플러**(시모·독고)가 세금리그 타령을 들고 옵니다 — 비추가 쏟아지지만 개의치 않습니다 |
| 더비 | `RIVALS` 표 31쌍. 슈퍼매치·동해안 더비처럼 **이름이 붙은 대결**은 반응의 양과 결이 다릅니다(대형 더비는 한 줄 더 시끄럽습니다) |
| 상황 | 승/무/패 · 3골 차 이상 · 역전승/역전패 · 무득점(슛을 많이 하고도 vs 아예 못 만든) · 무실점 |

> ⚠️ 예전에는 이 표의 **10종만** 쓰고 있었고, 그중 `bigWin`/`bigLose` 는 소셜에 없는 키라
> 대체 문구로 빠지고 있었습니다(실제 이름은 `winBig`/`loseBig`). 게다가
> `goalHigh/goalOk/goalLow` 는 **시즌 목표 공약**에 대한 반응인데 이것을 "골이 많이 났다"로
> 써서, 5골 경기에 *"감독이 우승 얘기했다는데... 진심인가?"* 같은 줄이 올라왔습니다.
> 지금은 쓰지 않습니다.

시즌이 없으므로 연승·순위·개막전·이적·구장 묶음은 쓰지 않습니다. 관중 반응(`crowd*`)과
수원 이스터에그는 추출기가 아직 안 가져옵니다 — 듀얼은 중립 경기라 관중이 없습니다.

### 브라우저 없이 확인하기

```bash
cd tools/realmatch && go run . -root ../.. -home ulsan -away jeonbuk -n 2
```

실제 명단으로 90분을 돌립니다. 선수 항목이 하나라도 빠지면 여기서 걸리고,
같은 라인업이면 지문이 같아야 하므로 **실제 데이터에서의 결정론**도 함께 봅니다.
경기 화면이 일꾼에게 넘기는 것과 **같은 모양**으로 라인업을 만들므로, 여기서 나온 지문은
브라우저에서 나오는 지문과 같습니다 (울산 vs 전북 = `deaca9c0` — goja·V8 양쪽에서 확인).

같은 구단끼리도 여기서 볼 수 있습니다. 한쪽 포메이션을 갈라 주면 됩니다.

```bash
cd tools/realmatch && go run . -root ../.. -home ulsan -away ulsan -awayform 3-5-2 -record
```

`-record` 를 붙이면 **선수 id 가 제 쪽에 있는지**까지 셉니다
(`명단 40명 (홈 20 · 원정 20) · id 갈림 정상`). 하나라도 섞이면 그 자리에서 중단합니다.

> ⚠️ 이 도구는 모듈을 이어 붙여 돌리므로 `export` 목록이 빠져도 통과합니다.
> 실제로 `kernel.js` 가 `F_` 를 내보내지 않아 **브라우저에서는 경기가 아예 시작되지 않는데도**
> 이 도구는 멀쩡히 돌던 적이 있습니다. 화면 확인을 완전히 대신하지는 못합니다.

### 연습 모드 (단계 A)

상대가 없어도 혼자 전술을 시험해 볼 수 있어야 한다는 의견을 받아 넣기로 했습니다.
팀마다 **3난이도 × 상대 전술 3종 = 아홉 가지** 연습 상대가 생깁니다.

난이도는 **능력치를 올려서 만들지 않습니다.** 그러면 "전력이 떨어져도 전술로 이기는 재미"가 무너집니다.
대신 상대 감독이 얼마나 유능한지를 바꿉니다 — 라인업을 잘 짜는가, 경기 중에 대응하는가,
내 전술을 보고 상성으로 골라 오는가.

연습 모드는 코드·링크 규격이 필요 없어서 **대전보다 먼저 나옵니다.** 자세한 설계는 설계서 단계 A.
